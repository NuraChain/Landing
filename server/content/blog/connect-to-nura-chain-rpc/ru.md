Всё, что программа делает с блокчейном, проходит через RPC-эндпоинт. Вот эндпоинт Nura Chain: что он делает, чего не делает и как направить на него привычные библиотеки.

## Эндпоинт

```text
https://rpc.nurachain.net
```

Он говорит на Ethereum JSON-RPC поверх HTTPS POST и принадлежит сети с chain ID `1020`. Это второе значение читайте у эндпоинта, а не отсюда:

```bash
curl -s https://rpc.nurachain.net -X POST \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_chainId","params":[]}'
```

`0x3fc` — это 1020. Каждой библиотеке ниже это число передаётся явно, и так задумано: клиент, которому сказали, какую сеть он ожидает, откажется продолжать, если эндпоинт не согласен, — и молчаливое развёртывание не в ту сеть превращается в ошибку при старте.

## Первый запрос, ничего не устанавливая

```bash
curl -s https://rpc.nurachain.net -X POST \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
```

Результаты возвращаются шестнадцатеричными величинами, а не десятичными числами, и на этом постоянно спотыкаются. `0x3aecc` — это 241 356. Любая клиентская библиотека переводит за вас; голый `curl` — нет.

## ethers.js

```javascript
import { JsonRpcProvider } from 'ethers';

const provider = new JsonRpcProvider('https://rpc.nurachain.net', {
    chainId: 1020,
    name: 'nura'
});

const [height, fees] = await Promise.all([
    provider.getBlockNumber(),
    provider.getFeeData()
]);

console.log(height, fees.maxFeePerGas);
```

Передача сети вторым аргументом делает две вещи: экономит один round trip `eth_chainId` при первом обращении и заставляет провайдер бросить исключение, если эндпоинт сообщает другую сеть. Второе и есть то, ради чего это стоит писать.

## viem

viem хочет объект chain — удобное место, чтобы держать все значения в одном объявлении:

```javascript
import { createPublicClient, defineChain, http } from 'viem';

export const nura = defineChain({
    id: 1020,
    name: 'Nura Mainnet',
    nativeCurrency: { name: 'Nura Coin', symbol: 'NURA', decimals: 18 },
    rpcUrls: { default: { http: ['https://rpc.nurachain.net'] } },
    blockExplorers: {
        default: { name: 'Nura Explorer', url: 'https://explorer.nurachain.net' }
    }
});

const client = createPublicClient({ chain: nura, transport: http() });

console.log(await client.getBlockNumber());
```

Этот же объект `nura` вы затем передаёте в wagmi и в wallet client самой viem.

## web3.py

```python
from web3 import Web3

w3 = Web3(Web3.HTTPProvider("https://rpc.nurachain.net"))

assert w3.eth.chain_id == 1020, "not the chain you think you are on"
print(w3.eth.block_number)
```

Написать это утверждение — три секунды, а спасло оно больше развёртываний, чем любая другая строка в этой статье.

## Чтение из браузера

Эндпоинт отдаёт разрешающие заголовки CORS, поэтому страница может обращаться к нему напрямую, без собственного прокси:

```javascript
const response = await fetch('https://rpc.nurachain.net', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ jsonrpc: '2.0', id: 1, method: 'eth_blockNumber', params: [] })
});

const { result } = await response.json();
```

Стоит ясно сказать, что именно это позволяет. Запросы на чтение работают из браузера. Всё, что требует приватного ключа, через этот эндпоинт не идёт вовсе — оно идёт через кошелёк пользователя, а это совершенно другой путь и тема материала [как собрать dApp на Nura Chain](/blog/build-a-dapp-on-nura-chain).

## Методы, которые отклоняются намеренно

Попросите у публичного эндпоинта аккаунты — он откажет:

```json
{"error":{"code":-32000,"message":"account unlock with HTTP access is forbidden"}}
```

Это правильное поведение, а не отсутствующая возможность. Публичный RPC-узел не хранит ключей от вашего имени, поэтому `eth_accounts`, `eth_sendTransaction` и `personal_*` попросту не над чем работать. Эндпоинт, который на них отвечал бы, был бы эндпоинтом, хранящим чьи-то средства.

Путь подписанной транзакции такой: соберите её локально, подпишите локально и отправьте подписанные байты через `eth_sendRawTransaction`. Любая библиотека делает это за вас, как только вы даёте ей кошелёк вместо голого провайдера.

## Практические замечания

- Не опрашивайте сеть на каждый рендер. Чтения из цепочки — сетевые вызовы; кэшируйте их на несколько секунд и разделяйте один запрос в полёте между вызывающими, пришедшими одновременно.
- Прочитайте chain ID один раз при старте и громко падайте при несовпадении, а не проверяйте на каждом вызове.
- Считайте неудавшееся чтение неудавшимся, а не нулём. Баланс, отрисованный как 0 из-за таймаута, хуже баланса, отрисованного как ошибка.
- Не зашивайте цену газа. Запрашивайте данные о комиссии в момент отправки; см. [как здесь устроены комиссии](/blog/nura-chain-evm-compatibility).

## Частые вопросы

### Есть ли ограничение по частоте запросов?

Считайте любой публичный эндпоинт ограниченным по частоте, объявлено это число или нет, и проектируйте соответственно: кэш, объединение запросов и отступ при сбое. Приложение, долбящее общий эндпоинт на каждое нажатие клавиши, рано или поздно где-нибудь придушат, и со стороны оператора это разумно.

### Можно ли использовать WebSockets или подписки?

Проверяйте, а не предполагайте. Если `eth_subscribe` недоступен, опрос `eth_blockNumber` с разумным интервалом — переносимый запасной вариант, к которому большинство приложений всё равно приходит.

### Почему моя транзакция никогда не подтверждается?

Обычная причина — прибитая цена газа, доставшаяся от шаблона и оказавшаяся ниже текущей базовой комиссии. Читайте данные о комиссии в момент отправки.

### Могу ли я поднять собственный узел?

Ничто из перечисленного не зависит от размещённого эндпоинта. Приложению, читающему с вашего узла, нужен лишь другой URL — и именно это свойство делает такую архитектуру стоящей.
