区块浏览器是你确认「自己做的事确实发生了」的地方。不是钱包声称的、不是脚本打印的，而是链上记录的。本文讲如何读 [Nura Explorer](https://explorer.nurachain.net)，以及最要紧的那个习惯：也别盲目相信它。

## 浏览器究竟是什么

它是读者，不是权威。浏览器运行一个节点、盯着每个区块，把看到的东西存进一个可检索的数据库——区块、交易和转账，建好索引，好让人按哈希或地址查。

这个区分很重要。浏览器什么都不决定。如果它和链不一致，那是链对、浏览器落后或出了故障。它展示的一切，都能直接从 RPC 端点取到——这正是最后一节要讲的。

## 找到一笔交易

每笔交易都有一个哈希——以 `0x` 开头的 66 个字符。钱包在发送后会显示它，部署脚本会打印它。把它粘进浏览器的搜索框。

如果什么都没返回，在断定东西丢了之前，有三种常见解释：

- 交易仍在待处理，尚未被打包进区块。
- 浏览器还没索引到包含它的那个区块。
- 它被广播到了另一条网络。这是最常见的一种，也正是链 ID 核验之所以重要的原因。

## 读一笔交易

值得理解的字段：

- **状态。** 成功或失败。失败的交易同样发生过，同样占了区块空间，同样花了 gas。「失败」不等于「没发生」——它意味着手续费花掉之后代码回滚了。
- **区块。** 哪个区块打包了它，以及此后其上又累积了多少区块。上面的区块越多，越是尘埃落定。
- **发送方 / 接收方。** 发送者，以及一个收款方或一份合约。部署交易的接收方为空，新建的合约会单独列出。
- **金额。** 有多少 NURA 作为原生资产发生了转移。代币转账在这里通常显示 `0`，因为代币是在合约内部移动的，而不是作为原生价值。这一点总让人意外。
- **消耗的 gas 与手续费。** 实际花费，通常低于设定的上限。
- **Nonce。** 发送方的交易计数器。它出现空洞，正是一笔卡住的交易会挡住同一账户后续所有交易的原因。

## 读一个地址

地址有两类，浏览器会加以区分。

外部拥有账户由私钥控制。它有余额和交易历史，仅此而已。

合约地址带有代码。如果你部署了东西而浏览器显示没有代码，那么无论脚本报告了什么，部署都没有成功——见[部署智能合约](/blog/deploy-a-smart-contract-on-nura-chain)。

对代币合约而言，有意思的部分是转账历史，因为那是 `Transfer` 事件日志，而不是一张余额表。任何钱包给你显示代币余额，用的都是同一份数据。

## 读一个区块

区块页面会显示高度、时间戳、打包的交易、相对上限的 gas 用量，以及当时的基础费。

Nura Chain 上的区块大约每三秒产生一个。gas 用量远低于上限，说明还有空间——那么一笔迟迟进不去的交易是被价格挤出去的，而不是被拥堵挤出去的，这把矛头指向手续费而非流量。

## 与 RPC 交叉核对

这是值得记住的一节。浏览器展示的任何数字，都可以直接向链求证：

```bash
curl -s https://rpc.nurachain.net -X POST \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionReceipt","params":["0xYourTxHash"]}'
```

回执带有 `status`——`0x1` 表示成功，`0x0` 表示回滚——外加区块号、gas 用量和事件日志。这才是权威答案。

合约同理：

```bash
curl -s https://rpc.nurachain.net -X POST \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getCode","params":["0xTheContract","latest"]}'
```

万一浏览器与端点不一致，请相信端点。更有用的做法是：当你即将对有价值的东西采取行动时，两边都查。两个独立读者相互印证，比一个自信的界面强得多。做法见[连接 Nura Chain RPC](/blog/connect-to-nura-chain-rpc)。

## 浏览器无法告诉你的事

- **一份合约是否安全。** 它展示代码和历史，不展示意图。已验证的合约是可读的合约，不是经过审计的合约。
- **一个代币是否正当。** 任何人都能部署一份用任意名字的合约。身份是地址。
- **一个地址归谁所有。** 地址是化名的。凡是出现的标签，都是浏览器运营方添加的，属于主张而非事实。
- **某件事为何失败。** 它显示交易回滚了；原因藏在合约自身的逻辑里。

## 常见问题

### 我的交易查不到，是不是丢了？

多半没有。用 `eth_getTransactionReceipt` 拿哈希去问 RPC。返回 null 表示尚未被打包——是待处理，不是消失。若始终不确认，通常是手续费的问题。

### 浏览器显示有代币转账，但金额是零，为什么？

因为代币的移动是合约状态变更，不是原生转账。`金额` 字段只跟踪 NURA。请改看同一笔交易里的代币转账部分。

### 合约「已验证」，我就能信任它吗？

验证意味着公开的源码能编译出所部署的字节码。它告诉你代码是什么，却不说明代码是否良好、作者是否诚实。

### 为什么浏览器显示的余额和我的钱包不一样？

通常是其中一方在另一条网络上，或者其中一方数据陈旧。用 `eth_getBalance` 问一下 RPC，就能定案。
